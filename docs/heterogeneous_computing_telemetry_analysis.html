The Joule Programming Language

Heterogeneous Computing & Hardware Telemetry: Deep Dive Analysis for Joule

Date: 2026-01-30 Purpose: Define Joule's strategy for GPU/TPU/NPU programming and comprehensive hardware telemetry

Executive Summary

To achieve Joule's mission of "Faster than C++. Safer than Rust. More efficient than anything," we must:

  1. Support all major compute accelerators: GPU (NVIDIA, AMD, Intel, Apple), TPU (Google), NPU (Intel, AMD, Qualcomm, Apple)
  2. Provide deep hardware telemetry: Not surface-level metrics, but comprehensive monitoring of energy, temperature, bandwidth, utilization across ALL hardware components
  3. Cross-platform portability: Windows, macOS, Linux, bare metal
  4. Energy-first optimization: Use telemetry data to make thermal-aware, energy-optimal decisions at compile-time and runtime

This document synthesizes 2026 state-of-the-art research on GPU programming models and hardware telemetry APIs to inform Joule's architecture.

1. GPU Programming Language Landscape

1.1 Mojo: The Current Leader in Heterogeneous Computing

Architecture: Built entirely on MLIR (Multi-Level Intermediate Representation), enabling compilation to CPUs, GPUs, TPUs, ASICs, FPGAs, and custom accelerators.

Key Features:

  • Performance portability: Single codebase targets NVIDIA GPUs, AMD MI300 GPUs, TPUs, and custom ASICs
  • Python ecosystem compatibility: Can reuse Python libraries while achieving C/C++ performance
  • AOT and JIT compilation: Flexibility for different deployment scenarios
  • Production-ready in Q1 2026: Compiler open-sourced in 2026

What Joule Must Match:

  • ✅ MLIR-based or equivalent multi-backend IR
  • ✅ Zero Python overhead (Joule doesn't need Python compat, but must be equally ergonomic)
  • ✅ Portable abstractions that compile to optimal code on each backend

Sources:

  • Mojo: MLIR-Based Performance-Portable HPC Science Kernels on GPUs for the Python Ecosystem
  • Mojo 🔥: Powerful CPU+GPU Programming
  • Mojo (programming language) - Wikipedia

1.2 NVIDIA CUDA Ecosystem (2026 State)

CUDA 13.1 (released 2025-2026) is the largest update to CUDA in 20 years:

Key Technologies:

  1. CUDA Tile: New tile-based programming model abstracting tensor cores and specialized hardware

    • Simplifies programming of tensor cores
    • Portable across NVIDIA GPU generations

  2. cuDNN (CUDA Deep Neural Network library):

    • High-performance GPU acceleration for neural networks
    • DEPRECATED on Blackwell+ GPUs when using CUDA 13
    • Being replaced by TensorRT for modern workloads

  3. TensorRT:

    • Inference compiler with quantization, layer fusion, kernel tuning
    • Low latency, high throughput for production AI
    • Now the preferred path over cuDNN

  4. Nsight Tools (2026.1.1):

    • Nsight Systems: CUDA API tracing, library profiling (cuBLAS, cuDNN, TensorRT)
    • Nsight Compute 2025.4: Profiling for CUDA Tile kernels, static SM partitioning
    • Multi-Process Service: Static SM partitioning for fine-grained GPU sharing
    • Compute Sanitizer: Compile-time memory error detection via NVCC

  5. CUDA-X Libraries:

    • cuBLAS: FP8/BF16 group GEMM on Blackwell
    • cuSPARSE: Sparse matrix operations
    • CUB/CCCL 3.1: Multi-phase determinism, collective primitives

What Joule Must Match:

  • ✅ Tile-based abstractions for tensor cores
  • ✅ Deep integration with profiling/telemetry (match Nsight's capabilities)
  • ✅ First-class tensor operations with automatic fusion

2. Hardware Telemetry: Comprehensive Monitoring Architecture

2.1 GPU Telemetry

NVIDIA (NVML - NVIDIA Management Library)

Capabilities:

  • GPU utilization (compute, memory, encoder, decoder)
  • GPU memory usage (used/free/total)
  • Temperature (GPU die, memory)
  • Power consumption (current, limit, average)
  • Clock speeds (core, memory)
  • Thermal throttling status
  • PCIe bandwidth utilization
  • ECC errors
  • Per-process GPU usage (which process is using which GPU)

APIs:

  • C library: libnvidia-ml.so (Linux), nvml.dll (Windows)
  • Python: pynvml
  • Cross-platform: Works on Linux, Windows, limited macOS support

Example Metrics:

nvmlDeviceGetUtilizationRates(device, &utilization);
// utilization.gpu (0-100%)
// utilization.memory (0-100%)

nvmlDeviceGetTemperature(device, NVML_TEMPERATURE_GPU, &temp);
// temp in Celsius

nvmlDeviceGetPowerUsage(device, &power);
// power in milliwatts

Sources:

  • NVIDIA gpu-monitoring-tools
  • Monitoring GPU performance on Linux VMs

AMD (ROCm / AMD SMI)

Capabilities (amd-smi tool, replacing rocm-smi):

APIs:

  • C library: libamd_smi.so

APIs:

  • Linux: perf_event_open(), /sys/class/powercap/intel-rapl/

  • Resource Director Technology (RDT): MBM, CMT, Cache Allocation Technology (CAT)

2.5 Storage Telemetry

Metrics:

  • Temperature: Current, max, critical thresholds

3. Proposed Joule Telemetry Architecture

3.1 Design Principles

  1. Zero-Cost Abstraction: Telemetry APIs compile to direct hardware access with no runtime overhead
  2. Opt-In by Default: Users explicitly request telemetry (avoid surprise overhead)
  3. Compile-Time and Runtime: Support both static (compile-time energy estimates) and dynamic (runtime monitoring)
  4. Cross-Platform Portability: Single Joule API works across Windows, macOS, Linux, bare metal
  5. Granular Control: Per-thread, per-device, per-operation monitoring

3.2 Proposed Joule Telemetry API

// Core telemetry module
mod energy {
    // Hardware energy readers (already implemented)
    pub struct EnergyMonitor { ... }
    pub enum ThermalState { Cool, Nominal, Elevated, Hot, Critical }
}

mod telemetry {
    use energy::{EnergyMonitor, ThermalState};

    // GPU telemetry
    pub trait GpuTelemetry {
        fn utilization(&self) -> Result<f64, Error>;  // 0.0-100.0%
        fn memory_used(&self) -> Result<u64, Error>;  // bytes
        fn temperature(&self) -> Result<f64, Error>;  // Celsius
        fn power_usage(&self) -> Result<f64, Error>;  // Watts
        fn clock_speed(&self) -> Result<(u32, u32), Error>;  // (core_mhz, mem_mhz)
    }

    // CPU telemetry
    pub struct CpuTelemetry {
        pub energy: EnergyMonitor,        // RAPL/equivalent
        pub thermal: ThermalState,
        pub frequency: Vec<u32>,          // Per-core MHz
        pub utilization: Vec<f64>,        // Per-core 0-100%
        pub cache_misses: u64,            // PMU counter
        pub instructions_retired: u64,    // PMU counter
    }

    // Memory telemetry
    pub struct MemoryTelemetry {
        pub bandwidth_read: f64,   // GB/s
        pub bandwidth_write: f64,  // GB/s
        pub numa_local_ratio: f64, // 0.0-1.0 (higher is better)
        pub capacity_used: u64,    // bytes
        pub capacity_total: u64,
    }

    // Storage telemetry
    pub struct StorageTelemetry {
        pub device_path: String,
        pub temperature: f64,              // Celsius
        pub wear_level: f64,               // 0.0-100.0% (percentage used)
        pub read_bandwidth: f64,           // MB/s
        pub write_bandwidth: f64,
        pub total_bytes_written: u64,
        pub errors: u64,
    }

    // Network telemetry
    pub struct NetworkTelemetry {
        pub interface: String,
        pub rx_bandwidth: f64,     // Mbps
        pub tx_bandwidth: f64,
        pub rx_packets: u64,
        pub tx_packets: u64,
        pub rx_errors: u64,
        pub tx_errors: u64,
    }

    // Unified system telemetry
    pub struct SystemTelemetry {
        pub cpu: CpuTelemetry,
        pub gpus: Vec<Box<dyn GpuTelemetry>>,
        pub memory: MemoryTelemetry,
        pub storage: Vec<StorageTelemetry>,
        pub network: Vec<NetworkTelemetry>,
    }

    impl SystemTelemetry {
        // Snapshot current state
        pub fn snapshot() -> Result<Self, Error>;

        // Continuous monitoring
        pub fn monitor(interval_ms: u64, callback: fn(Self)) -> MonitorHandle;
    }
}

// Example usage
fn main() {
    // Single snapshot
    let telemetry = telemetry::SystemTelemetry::snapshot()?;
    println!("GPU 0 temp: {:.1}°C", telemetry.gpus[0].temperature()?);
    println!("CPU energy: {:.3} J", telemetry.cpu.energy.read_energy()?);

    // Continuous monitoring
    let handle = telemetry::SystemTelemetry::monitor(1000, |snapshot| {
        if snapshot.cpu.thermal == ThermalState::Hot {
            warn!("CPU overheating, throttling workload");
        }
    });

    // ... do work ...

    handle.stop();
}

3.3 Implementation Strategy

Phase 1: Core Telemetry (Current)

  • ✅ Linux RAPL energy monitoring
  • ✅ Thermal state detection (5-level)
  • ✅ Cross-platform abstraction (Linux, macOS stub, Windows stub)

Phase 2: GPU Telemetry (Month 7-8)

Linux:

  • NVIDIA: Link against libnvidia-ml.so (NVML)
  • AMD: Link against libamd_smi.so
  • Intel: Parse intel_gpu_top output or use OpenVINO

Windows:

  • NVIDIA: nvml.dll
  • AMD: amd_smi.dll
  • Query via WMI as fallback

macOS:

  • Metal: IOKit queries
  • Limited support (Metal is proprietary)

Phase 3: Full System Telemetry (Month 9-10)

  • CPU: PMU via perf_event_open() (Linux), Performance Counters API (Windows), kperf (macOS)
  • Memory: NUMA awareness via hwloc, PMU events for bandwidth
  • Storage: NVMe via libnvme (Linux), SMART via smartctl wrapper
  • Network: /sys/class/net/ (Linux), Performance Counters (Windows), ioctl (macOS)

Phase 4: Bare Metal & Enterprise (Year 2)

  • IPMI/Redfish support for server environments
  • NVIDIA DCGM integration for GPU clusters
  • Custom kernel modules for lowest-latency access

5. Recommended Joule Architecture

5.1 Compiler Backend Strategy

Three-tier approach:

  1. Tier 1 (Direct native support):

    • NVIDIA CUDA (via LLVM NVPTX backend)
    • AMD HIP (via LLVM AMDGPU backend)
    • Apple Metal (via LLVM Metal backend or AIR)

  2. Tier 2 (SPIR-V/SYCL abstraction):

    • Compile Joule → SPIR-V → Vulkan Compute (Intel, mobile GPUs)
    • Provide SYCL-like kernel syntax

  3. Tier 3 (Cloud/API-based):

    • Google Cloud TPU (via XLA/JAX codegen)
    • Intel NPU (via OpenVINO IR)
    • Qualcomm NPU (via SNPE)

MLIR Integration:

  • Use MLIR as Joule's MIR (Mid-level IR)
  • Leverage existing MLIR dialects: gpu, linalg, tensor, scf
  • Energy optimizer pass operates on MLIR before lowering to LLVM/SPIR-V

5.3 Kernel Syntax (Portable GPU Programming)

Goal: Make GPU programming as easy as writing CPU code

use compute::portable::{Kernel, ThreadIdx, BlockIdx};

// Portable kernel (compiles to CUDA, HIP, Metal, Vulkan)
#[kernel]
fn vector_add(a: &[f32], b: &[f32], c: &mut [f32]) {
    let idx = ThreadIdx::x() + BlockIdx::x() * BlockDim::x();
    if idx < a.len() {
        c[idx] = a[idx] + b[idx];
    }
}

fn main() {
    let a = vec![1.0f32; 1_000_000];
    let b = vec![2.0f32; 1_000_000];
    let mut c = vec![0.0f32; 1_000_000];

    // Automatically selects best available GPU
    vector_add.launch((a.len() / 256, 256), &a, &b, &mut c)?;

    // Check first element
    assert_eq!(c[0], 3.0);
}

Thermal-Aware Execution:

use telemetry::SystemTelemetry;
use energy::ThermalState;

fn matrix_multiply(a: &[f32], b: &[f32]) -> Vec<f32> {
    let telemetry = SystemTelemetry::snapshot()?;

    match telemetry.cpu.thermal {
        ThermalState::Cool | ThermalState::Nominal => {
            // Use SIMD (AVX-512) - more energy-efficient when cool
            matrix_multiply_simd(a, b)
        }
        ThermalState::Hot | ThermalState::Critical => {
            // Fall back to scalar - avoids thermal throttling
            matrix_multiply_scalar(a, b)
        }
        _ => {
            // Elevated: conservative SIMD (AVX2 instead of AVX-512)
            matrix_multiply_simd_conservative(a, b)
        }
    }
}

7. Open Questions & Research Needed

  1. MLIR Learning Curve: Do we invest in MLIR or build custom MIR?

    • Recommendation: Use MLIR. It's proven (TensorFlow, Mojo, LLVM), saves years of development.

  2. Portable Kernel Limitations: What GPU features can't be abstracted?

    • Tensor cores (NVIDIA), Matrix cores (AMD), AMX (Intel) - need vendor-specific paths

  3. NPU Fragmentation: How to unify Intel/AMD/Apple/Qualcomm NPUs?

    • Recommendation: ONNX Runtime as common IR, compile Joule → ONNX for NPUs

  4. Telemetry Overhead: How much does continuous monitoring cost?

    • Need to benchmark sampling rate vs. overhead (target: <1% CPU overhead at 1 Hz sampling)

  5. Bare Metal Deployment: How to support OS-less environments?

    • Direct hardware register access, no stdlib
    • May need #[no_std] kernels with manual DMA

8. Conclusion

Joule has a clear path to exceed Mojo and CUDA in the heterogeneous computing space:

What Joule Must Deliver:

  1. Performance Portability (like Mojo):

    • ✅ MLIR-based compilation
    • ✅ Single source, multi-target (CUDA, HIP, Metal, Vulkan, TPU)

  2. Deep Telemetry (beyond anyone):

    • ✅ GPU, CPU, RAM, storage, network monitoring
    • ✅ Built into standard library, not external tools
    • ✅ Zero-cost abstraction over vendor APIs (NVML, ROCm, etc.)

  3. Energy-First Optimization (unique to Joule):

    • ✅ Thermal-aware instruction selection (SIMD vs. scalar)
    • ✅ DRAM row buffer-aware memory layout
    • ✅ Power-gating-aware register allocation
    • ✅ Compile-time energy budgeting

  4. Memory Safety (like Rust, unlike Mojo/CUDA):

    • ✅ Ownership and borrow checking
    • ✅ Safe GPU memory management (no double-free, use-after-free)

  5. Productivity (like Mojo, better than CUDA):

    • ✅ Ergonomic syntax
    • ✅ Excellent error messages (like Rust)
    • ✅ Fast compilation (Cranelift for dev, LLVM for release)

Timeline:

  • Month 7-8: GPU telemetry (NVML, ROCm)
  • Month 9-10: Energy optimizer passes (thermal-aware, DRAM-aware)
  • Month 11-12: GPU backends (CUDA, HIP, Metal via LLVM)
  • Year 2: TPU/NPU support, bare metal deployment, production hardening

The result: Joule becomes the first language that delivers on the promise of "write once, run optimally everywhere" for the heterogeneous computing era—and it's the only language that makes energy a first-class concern.
