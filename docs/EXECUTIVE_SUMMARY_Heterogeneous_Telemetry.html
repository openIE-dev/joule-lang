The Joule Programming Language

Executive Summary: Joule's Heterogeneous Computing & Telemetry Strategy

Date: 2026-01-30 Status: Research Complete → Architecture Design Phase

Key Findings

1. Mojo Sets the Bar for Multi-Backend Compilation

What Mojo Does Right:

  • MLIR-based architecture enables targeting NVIDIA GPUs, AMD GPUs, TPUs, CPUs from single source
  • Production-ready in Q1 2026 (compiler just open-sourced)
  • Python ecosystem compatibility (not relevant for Joule, but shows ergonomics matter)

What Joule Must Match:

  • ✅ MLIR-based MIR layer for multi-target compilation
  • ✅ Performance portability (same code, optimal performance on each backend)
  • ✅ Compile to CUDA (NVIDIA), HIP (AMD), Metal (Apple), Vulkan (Intel/mobile)

2. NVIDIA CUDA 13.1 Introduces Major Paradigm Shift

CUDA Tile = New tile-based programming model for tensor cores (biggest CUDA update in 20 years)

What This Means for Joule:

  • Can't just target "old CUDA" - must support modern tile abstractions
  • TensorRT replacing cuDNN on Blackwell GPUs → AI inference is moving toward compiler-based optimization (good for Joule!)
  • Nsight profiling tools are industry-leading → Joule must provide comparable telemetry

Joule's Edge:

  • Energy-aware from day 1: CUDA doesn't optimize for joules, only FLOPS
  • Cross-vendor: CUDA locks users into NVIDIA

5. Energy-First Optimization is Joule's Killer Feature

What Nobody Else Does:

  • Choose scalar vs. SIMD based on CPU temperature (avoid thermal throttling)
  • Optimize memory layout for DRAM row buffer hits (100× energy difference)
  • Track GPU power spikes and adjust workload distribution
  • Compile-time energy budgeting (user specifies max joules, compiler optimizes)

Validation Needed:

  • Benchmark thermal-aware SIMD selection (expect 30-50% energy reduction on hot CPUs)
  • Measure DRAM row buffer optimization impact (expect 20-40% energy reduction)

Critical Architecture Decisions

Decision 1: Use MLIR for Joule's MIR

Rationale:

  • Proven technology (TensorFlow, Mojo, LLVM)
  • Existing GPU dialect (gpu, linalg, tensor)
  • Saves 2-3 years of development vs. custom IR
  • Enables targeting TPUs via XLA/IREE

Action: Integrate MLIR into compiler pipeline at MIR stage

Decision 2: Three-Tier GPU Backend Strategy

Tier 1 (Direct LLVM Backends):

  • NVIDIA: LLVM NVPTX → PTX → CUDA
  • AMD: LLVM AMDGPU → GCN/RDNA
  • Apple: LLVM Metal → AIR

Tier 2 (SPIR-V for Portability):

  • Intel, mobile GPUs: Joule → MLIR → SPIR-V → Vulkan Compute
  • Future-proof (SPIR-V is vendor-neutral)

Tier 3 (Cloud/Specialized):

  • TPU: MLIR → XLA → TPU ISA
  • Intel NPU: MLIR → OpenVINO IR
  • Qualcomm NPU: ONNX Runtime

Decision 3: Telemetry API in Standard Library

Module Structure:

stdlib/telemetry/
├── gpu.joule      # GpuTelemetry trait, vendor impls
├── cpu.joule      # RAPL, PMU, thermal
├── memory.joule   # Bandwidth, NUMA
├── storage.joule  # NVMe SMART
├── network.joule  # Interface stats
└── system.joule   # Unified snapshot API

Implementation:

  • Rust FFI to vendor libraries (NVML, ROCm, libnvme, etc.)
  • Zero-cost abstraction (compiles to direct syscalls/library calls)
  • Graceful degradation (return Error::Unsupported on unavailable platforms)

Proposed Joule Kernel Syntax

Portable GPU Kernel (write once, compile to CUDA/HIP/Metal/Vulkan):

use compute::portable::{Kernel, ThreadIdx, BlockIdx, BlockDim};

#[kernel]
fn vector_add(a: &[f32], b: &[f32], c: &mut [f32]) {
    let idx = ThreadIdx::x() + BlockIdx::x() * BlockDim::x();
    if idx < a.len() {
        c[idx] = a[idx] + b[idx];
    }
}

fn main() {
    let a = vec![1.0; 1_000_000];
    let b = vec![2.0; 1_000_000];
    let mut c = vec![0.0; 1_000_000];

    // Launch on best available GPU (CUDA, HIP, Metal, or Vulkan)
    vector_add.launch((1000, 1000), &a, &b, &mut c)?;

    assert_eq!(c[0], 3.0);
}

Thermal-Aware CPU Code:

use telemetry::SystemTelemetry;

fn matrix_multiply(a: &Matrix, b: &Matrix) -> Matrix {
    let system = SystemTelemetry::snapshot()?;

    // Compiler optimizes based on runtime thermal state
    match system.cpu.thermal {
        ThermalState::Cool => {
            // Aggressive SIMD (AVX-512)
            matrix_multiply_avx512(a, b)
        }
        ThermalState::Hot => {
            // Scalar fallback (avoids thermal throttling)
            matrix_multiply_scalar(a, b)
        }
        _ => {
            // Conservative SIMD (AVX2)
            matrix_multiply_avx2(a, b)
        }
    }
}

Risks and Mitigations

Risk 1: MLIR Learning Curve

Impact: High Mitigation: Start with simple MLIR integration (use existing dialects), leverage Mojo's open-source compiler as reference

Risk 2: Vendor API Fragmentation

Impact: Medium Mitigation: Prioritize NVIDIA (largest ecosystem), gracefully degrade on unsupported platforms

Risk 3: Energy Optimizer Not Delivering Claimed Savings

Impact: Critical (undermines core value prop) Mitigation:

  • Validate with PoC before Month 9 (thermal-aware SIMD selection)
  • Continuous benchmarking against LLVM -O3, Rust, C++
  • If not achieving 50%+ savings by Month 10, pivot to "match performance, use less energy" positioning

Risk 4: GPU Kernel Portability Limitations

Impact: Medium Mitigation: Document vendor-specific extensions (tensor cores, warp intrinsics), provide opt-in #[target(cuda)] attributes
