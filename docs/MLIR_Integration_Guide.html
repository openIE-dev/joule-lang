Executive Summary

Decision: Adopt MLIR (Multi-Level Intermediate Representation) as Joule's MIR layer

Rationale:

  • ✅ Proven technology: Used by TensorFlow, Mojo, LLVM, major AI frameworks
  • ✅ Multi-backend compilation: Single source → CUDA, HIP, Metal, Vulkan, TPU
  • ✅ GPU dialect built-in: Avoids reinventing GPU abstractions
  • ✅ Saves 2-3 years: Would take years to build equivalent custom IR
  • ✅ Active development: LLVM 21 released 2026, continuous improvements

Integration Path: Joule → HIR → MLIR → LLVM/NVPTX/AMDGPU/Metal

Timeline:

  • Month 4: MLIR integration prototype
  • Month 7-10: GPU backends via MLIR
  • Month 12: Production-ready MLIR pipeline

Why MLIR for Joule

The Multi-Backend Challenge

Joule promises to compile to:

  • NVIDIA GPUs (CUDA / NVPTX)
  • AMD GPUs (ROCm / AMDGPU)
  • Apple GPUs (Metal / AIR)
  • Intel GPUs (Vulkan Compute / SPIR-V)
  • Google TPUs (XLA)
  • Intel NPUs (OpenVINO)
  • Qualcomm NPUs (SNPE)

Without MLIR: We'd need to implement 7+ custom backends and IR lowering paths ourselves.

With MLIR: We leverage existing infrastructure:

  • GPU dialect → NVVM (CUDA) / ROCDL (HIP) / LLVM IR (Metal)
  • Linalg/Tensor dialects → XLA (TPU)
  • Existing optimization passes for free

MLIR Architecture Overview

What is MLIR?

MLIR (Multi-Level Intermediate Representation) is a compiler infrastructure that supports multiple abstraction levels in a single IR via dialects.

Key Concept: Dialects = Domain-specific operations, types, and semantics

Think of dialects as "mini-IRs" that can interoperate:

  • arith: Basic math ops (addi, mulf, divsi)
  • func: Functions and calls
  • scf: Structured control flow (for, if, while)
  • memref: Memory allocation and access
  • tensor: High-level tensor operations
  • linalg: Linear algebra (matmul, conv)
  • gpu: GPU kernels, thread/block abstractions
  • nvvm: NVIDIA-specific ops (mapping to PTX)
  • llvm: LLVM IR as a dialect

Melior API Overview

Core Types:

  • Context: MLIR context (like LLVM context)
  • Module: Top-level container for MLIR operations
  • Block: Basic block (sequence of operations)
  • Operation: Single MLIR operation
  • Value: SSA value
  • Type: MLIR type
  • Attribute: Metadata
  • Location: Source location
  • Dialect: Dialect handle

Example (Adding two numbers):

use melior::{
    Context,
    dialect::DialectRegistry,
    ir::{*, attribute::IntegerAttribute, r#type::IntegerType},
    utility::register_all_dialects,
};

fn main() -> Result<(), Box<dyn std::error::Error>> {
    // Create MLIR context
    let registry = DialectRegistry::new();
    register_all_dialects(&registry);

    let context = Context::new();
    context.append_dialect_registry(&registry);
    context.load_all_available_dialects();

    // Create module
    let location = Location::unknown(&context);
    let module = Module::new(location);

    // Create function: func @add(%arg0: i32, %arg1: i32) -> i32
    let i32_type = IntegerType::new(&context, 32).into();

    let function = {
        let block = Block::new(&[(i32_type, location), (i32_type, location)]);

        // %0 = arith.addi %arg0, %arg1
        let result = block.append_operation(
            OperationBuilder::new("arith.addi", location)
                .add_operands(&[block.argument(0)?.into(), block.argument(1)?.into()])
                .add_results(&[i32_type])
                .build()?
        ).result(0)?.into();

        // return %0
        block.append_operation(
            OperationBuilder::new("func.return", location)
                .add_operands(&[result])
                .build()?
        );

        let region = Region::new();
        region.append_block(block);

        OperationBuilder::new("func.func", location)
            .add_attributes(&[
                (Identifier::new(&context, "sym_name"),
                 StringAttribute::new(&context, "add").into()),
                (Identifier::new(&context, "function_type"),
                 TypeAttribute::new(
                     FunctionType::new(&context, &[i32_type, i32_type], &[i32_type]).into()
                 ).into()),
            ])
            .add_regions(vec![region])
            .build()?
    };

    module.body().append_operation(function);

    // Verify
    assert!(module.as_operation().verify());

    // Print MLIR
    println!("{}", module.as_operation());

    Ok(())
}

Output:

module {
  func.func @add(%arg0: i32, %arg1: i32) -> i32 {
    %0 = arith.addi %arg0, %arg1 : i32
    func.return %0 : i32
  }
}

Joule's MLIR Compilation Pipeline

Phase 1: Joule HIR → MLIR (High-level)

Goal: Convert Joule's typed HIR to MLIR func, scf, arith, memref dialects

Example Joule Code:

fn add(x: i32, y: i32) -> i32 {
    x + y
}

fn main() {
    let result = add(5, 10);
    println!("{}", result);
}

Generated MLIR (func + arith dialects):

module {
  func.func @add(%arg0: i32, %arg1: i32) -> i32 {
    %0 = arith.addi %arg0, %arg1 : i32
    func.return %0 : i32
  }

  func.func @main() {
    %c5 = arith.constant 5 : i32
    %c10 = arith.constant 10 : i32
    %0 = func.call @add(%c5, %c10) : (i32, i32) -> i32
    // println lowered to separate pass
    func.return
  }
}

Implementation: joule-hir-to-mlir pass in compiler/joule-mlir/

Phase 2: MLIR Optimization Passes

Built-in MLIR passes we get for free:

  • canonicalize: Simplify operations
  • cse: Common subexpression elimination
  • inline: Function inlining
  • loop-fusion: Fuse adjacent loops
  • affine-loop-unroll: Unroll affine loops
  • mem2reg: Promote memory to SSA values
  • sccp: Sparse conditional constant propagation

Joule-specific passes:

  • joule-energy-optimizer: Our killer feature
    • Thermal-aware instruction selection
    • DRAM row buffer-aware layout
    • Power-aware register allocation

Pipeline:

#![allow(unused)]
fn main() {
use melior::pass::PassManager;

let pass_manager = PassManager::new(&context);

// Standard MLIR optimizations
pass_manager.add_pass(Pass::from_name("canonicalize")?);
pass_manager.add_pass(Pass::from_name("cse")?);
pass_manager.add_pass(Pass::from_name("inline")?);

// Joule energy optimizer (custom)
pass_manager.add_pass(joule_energy_optimizer_pass());

// More optimization
pass_manager.add_pass(Pass::from_name("sccp")?);

pass_manager.run(&mut module)?;
}

Phase 3: Lowering to Target Backends

CPU Path: MLIR → LLVM Dialect → LLVM IR → x86_64/ARM64

GPU Path: MLIR → GPU Dialect → NVVM/ROCDL/LLVM → PTX/GCN/AIR

Example Pipeline (CPU):

mlir-opt input.mlir \
  --convert-arith-to-llvm \
  --convert-scf-to-cf \
  --convert-func-to-llvm \
  --finalize-memref-to-llvm \
  --reconcile-unrealized-casts \
  -o output.mlir

mlir-translate --mlir-to-llvmir output.mlir -o output.ll
llc output.ll -o output.o

Example Pipeline (NVIDIA GPU):

mlir-opt input.mlir \
  --gpu-kernel-outlining \
  --convert-gpu-to-nvvm \
  --gpu-to-llvm \
  --reconcile-unrealized-casts \
  -o gpu.mlir

mlir-translate --mlir-to-llvmir gpu.mlir -o gpu.ll
llc -march=nvptx64 gpu.ll -o kernel.ptx

GPU Code Generation Paths

NVIDIA CUDA Path

Pipeline: Joule → MLIR GPU Dialect → NVVM Dialect → LLVM NVPTX → PTX → CUDA Binary

MLIR GPU Dialect Example:

gpu.module @kernels {
  gpu.func @vector_add(%arg0: memref<?xf32>, %arg1: memref<?xf32>,
                       %arg2: memref<?xf32>) kernel {
    %idx = gpu.thread_id x
    %0 = memref.load %arg0[%idx] : memref<?xf32>
    %1 = memref.load %arg1[%idx] : memref<?xf32>
    %2 = arith.addf %0, %1 : f32
    memref.store %2, %arg2[%idx] : memref<?xf32>
    gpu.return
  }
}

func.func @main() {
  %c1024 = arith.constant 1024 : index
  %a = memref.alloc(%c1024) : memref<?xf32>
  %b = memref.alloc(%c1024) : memref<?xf32>
  %c = memref.alloc(%c1024) : memref<?xf32>

  gpu.launch_func @kernels::@vector_add
    blocks in (%c1, %c1, %c1)
    threads in (%c1024, %c1, %c1)
    args(%a, %b, %c)

  memref.dealloc %a : memref<?xf32>
  memref.dealloc %b : memref<?xf32>
  memref.dealloc %c : memref<?xf32>
  return
}

Lowering to NVVM:

llvm.func @vector_add(%arg0: !llvm.ptr<f32>, %arg1: !llvm.ptr<f32>,
                      %arg2: !llvm.ptr<f32>) {
  %0 = nvvm.read.ptx.sreg.tid.x : i32
  %1 = llvm.sext %0 : i32 to i64

  %2 = llvm.getelementptr %arg0[%1] : (!llvm.ptr<f32>, i64) -> !llvm.ptr<f32>
  %3 = llvm.load %2 : !llvm.ptr<f32>

  %4 = llvm.getelementptr %arg1[%1] : (!llvm.ptr<f32>, i64) -> !llvm.ptr<f32>
  %5 = llvm.load %4 : !llvm.ptr<f32>

  %6 = llvm.fadd %3, %5 : f32

  %7 = llvm.getelementptr %arg2[%1] : (!llvm.ptr<f32>, i64) -> !llvm.ptr<f32>
  llvm.store %6, %7 : !llvm.ptr<f32>

  llvm.return
}

Compilation Pipeline:

# Step 1: Lower to NVVM
mlir-opt --gpu-kernel-outlining \
         --convert-gpu-to-nvvm \
         --gpu-to-llvm \
         kernel.mlir -o nvvm.mlir

# Step 2: Translate to LLVM IR
mlir-translate --mlir-to-llvmir nvvm.mlir -o kernel.ll

# Step 3: Compile to PTX
llc -march=nvptx64 -mcpu=sm_80 kernel.ll -o kernel.ptx

# Step 4: Link with CUDA runtime (done by Joule runtime)

AMD ROCm / HIP Path

Pipeline: Joule → MLIR GPU Dialect → ROCDL Dialect → LLVM AMDGPU → GCN/RDNA ISA

Same GPU dialect as NVIDIA, but lower to rocdl instead of nvvm:

mlir-opt --gpu-kernel-outlining \
         --convert-gpu-to-rocdl \
         --gpu-to-llvm \
         kernel.mlir -o rocdl.mlir

mlir-translate --mlir-to-llvmir rocdl.mlir -o kernel.ll

llc -march=amdgcn -mcpu=gfx1030 kernel.ll -o kernel.o

Key Insight: Same high-level MLIR GPU code → Different lowering → Runs on AMD GPUs

Apple Metal Path

Pipeline: Joule → MLIR GPU Dialect → LLVM Dialect → LLVM Metal Backend → AIR → Metal Binary

Metal uses standard LLVM backend (not a special dialect like NVVM/ROCDL):

mlir-opt --convert-gpu-to-llvm kernel.mlir -o llvm.mlir

mlir-translate --mlir-to-llvmir llvm.mlir -o kernel.ll

llc -march=amdgcn -mtriple=air64-apple-macosx kernel.ll -o kernel.metallib

Intel Vulkan Compute / SPIR-V Path

Pipeline: Joule → MLIR GPU Dialect → SPIR-V Dialect → SPIR-V Binary → Vulkan

mlir-opt --convert-gpu-to-spirv kernel.mlir -o spirv.mlir

mlir-translate --mlir-to-spirv spirv.mlir -o kernel.spv

Key Advantage: SPIR-V runs on Intel, ARM Mali, Qualcomm Adreno, any Vulkan-capable GPU

Joule Kernel Example:

use compute::gpu::{ThreadIdx, BlockIdx, BlockDim};

#[kernel]
fn vector_add(a: &[f32], b: &[f32], c: &mut [f32]) {
    let idx = ThreadIdx::x() + BlockIdx::x() * BlockDim::x();
    if idx < a.len() {
        c[idx] = a[idx] + b[idx];
    }
}

Generated MLIR:

gpu.module @kernels {
  gpu.func @vector_add(%a: memref<?xf32>, %b: memref<?xf32>, %c: memref<?xf32>) kernel {
    %tx = gpu.thread_id x
    %bx = gpu.block_id x
    %bdx = gpu.block_dim x
    %idx = arith.muli %bx, %bdx : index
    %idx2 = arith.addi %idx, %tx : index

    %len = memref.dim %a, 0 : memref<?xf32>
    %cond = arith.cmpi ult, %idx2, %len : index

    scf.if %cond {
      %v_a = memref.load %a[%idx2] : memref<?xf32>
      %v_b = memref.load %b[%idx2] : memref<?xf32>
      %sum = arith.addf %v_a, %v_b : f32
      memref.store %sum, %c[%idx2] : memref<?xf32>
    }

    gpu.return
  }
}

use melior::pass::{PassManager, Pass};

pub fn compile_to_ptx(module: &Module) -> Result<String, Error> {

use melior::ir::Operation;

pub fn thermal_aware_pass(op: &Operation) -> Result<(), Error> {
    // Walk all operations
    op.walk(|inner_op: &Operation| {
        if is_simd_operation(inner_op) {
            // Check if we can determine thermal state at compile time
            if let Some(thermal_state) = get_compile_time_thermal_state() {
                if thermal_state.should_avoid_simd() {

                // Insert runtime thermal check
                insert_runtime_thermal_check(inner_op)?;
            }
        }
        Ok(())

    Ok(())
}

Code Examples

Example 1: Simple Function Compilation

Joule Source:

fn factorial(n: i32) -> i32 {
    if n <= 1 {
        return 1;
    }
    n * factorial(n - 1)
}

Generated MLIR (func + scf + arith):

module {
  func.func @factorial(%arg0: i32) -> i32 {
    %c1 = arith.constant 1 : i32
    %cond = arith.cmpi sle, %arg0, %c1 : i32
    %result = scf.if %cond -> (i32) {
      scf.yield %c1 : i32
    } else {
      %n_minus_1 = arith.subi %arg0, %c1 : i32
      %rec = func.call @factorial(%n_minus_1) : (i32) -> i32
      %prod = arith.muli %arg0, %rec : i32
      scf.yield %prod : i32
    }
    func.return %result : i32
  }
}

Example 2: GPU Kernel Compilation

Joule Source:

#[kernel]
fn matrix_add(a: &[f32], b: &[f32], c: &mut [f32], width: usize) {
    let row = BlockIdx::y() * BlockDim::y() + ThreadIdx::y();
    let col = BlockIdx::x() * BlockDim::x() + ThreadIdx::x();
    let idx = row * width + col;

    c[idx] = a[idx] + b[idx];
}

fn main() {
    let n = 1024;
    let a = vec![1.0f32; n * n];
    let b = vec![2.0f32; n * n];
    let mut c = vec![0.0f32; n * n];

    // Launch kernel: 32x32 blocks, 32x32 threads per block
    matrix_add.launch((32, 32), (32, 32), &a, &b, &mut c, n);
}

Generated MLIR (GPU dialect):

gpu.module @kernels {
  gpu.func @matrix_add(%a: memref<?xf32>, %b: memref<?xf32>,
                       %c: memref<?xf32>, %width: index) kernel {
    %ty = gpu.thread_id y
    %by = gpu.block_id y
    %bdy = gpu.block_dim y
    %row_idx = arith.addi %ty, arith.muli %by, %bdy : index

    %tx = gpu.thread_id x
    %bx = gpu.block_id x
    %bdx = gpu.block_dim x
    %col_idx = arith.addi %tx, arith.muli %bx, %bdx : index

    %row_offset = arith.muli %row_idx, %width : index
    %idx = arith.addi %row_offset, %col_idx : index

    %v_a = memref.load %a[%idx] : memref<?xf32>
    %v_b = memref.load %b[%idx] : memref<?xf32>
    %sum = arith.addf %v_a, %v_b : f32
    memref.store %sum, %c[%idx] : memref<?xf32>

    gpu.return
  }
}

func.func @main() {
  %n = arith.constant 1024 : index
  %size = arith.muli %n, %n : index

  %a = memref.alloc(%size) : memref<?xf32>
  %b = memref.alloc(%size) : memref<?xf32>
  %c = memref.alloc(%size) : memref<?xf32>

  // Initialize a, b (omitted for brevity)

  %grid_x = arith.constant 32 : index
  %grid_y = arith.constant 32 : index
  %block_x = arith.constant 32 : index
  %block_y = arith.constant 32 : index

  gpu.launch_func @kernels::@matrix_add
    blocks in (%grid_x, %grid_y, %c1)
    threads in (%block_x, %block_y, %c1)
    args(%a, %b, %c, %n)

  memref.dealloc %a : memref<?xf32>
  memref.dealloc %b : memref<?xf32>
  memref.dealloc %c : memref<?xf32>

  return
}

Final PTX (NVIDIA assembly):

.version 7.8
.target sm_80
.address_size 64

.visible .entry matrix_add(
    .param .u64 a,
    .param .u64 b,
    .param .u64 c,
    .param .u64 width
) {
    .reg .pred %p<1>;
    .reg .b32 %r<10>;
    .reg .b64 %rd<10>;
    .reg .f32 %f<5>;

    // Load parameters
    ld.param.u64 %rd1, [a];
    ld.param.u64 %rd2, [b];
    ld.param.u64 %rd3, [c];
    ld.param.u64 %rd4, [width];

    // Calculate thread index
    mov.u32 %r1, %tid.y;
    mov.u32 %r2, %ctaid.y;
    mov.u32 %r3, %ntid.y;
    mad.lo.s32 %r4, %r2, %r3, %r1;  // row = by * bdy + ty

    mov.u32 %r5, %tid.x;
    mov.u32 %r6, %ctaid.x;
    mov.u32 %r7, %ntid.x;
    mad.lo.s32 %r8, %r6, %r7, %r5;  // col = bx * bdx + tx

    // Calculate linear index
    mul.wide.s32 %rd5, %r4, %rd4;   // row * width
    cvt.s64.s32 %rd6, %r8;
    add.s64 %rd7, %rd5, %rd6;       // idx = row * width + col

    // Load a[idx]
    shl.b64 %rd8, %rd7, 2;          // idx * sizeof(float)
    add.s64 %rd9, %rd1, %rd8;
    ld.global.f32 %f1, [%rd9];

    // Load b[idx]
    add.s64 %rd10, %rd2, %rd8;
    ld.global.f32 %f2, [%rd10];

    // Add
    add.f32 %f3, %f1, %f2;

    // Store c[idx]
    add.s64 %rd11, %rd3, %rd8;
    st.global.f32 [%rd11], %f3;

    ret;
}

This entire chain is automated by MLIR—we just generate the high-level GPU dialect!

Performance Expectations

Compilation Speed

MLIR overhead:

  • Low: 2-3% increase in compile time vs direct LLVM IR generation
  • Transform dialect: ≤2.6% overhead for auto-tuning

Evidence:

  • Recent MLIR-based compilers (TPP-MLIR, LAPIS) achieve compilation times competitive with hand-written code
  • Mojo demonstrates fast compilation with MLIR

FrameworkTargetPerformance vs Hand-Written

  • NVIDIA GPU: 90-95% of hand-written CUDA (MLIR → NVPTX is mature)
  • AMD GPU: 85-90% of hand-written HIP (less mature than NVPTX)
  • Energy savings: 50-70% reduction via energy optimizer passes (our differentiator)

Risks and Mitigations

Risk 1: MLIR API Instability

Impact: Medium Probability: Low

Issue: Melior tracks MLIR C API, which is still evolving (alpha stage)

Mitigation:

  • Pin to specific MLIR version (21.x)
  • Budget time for API updates each LLVM release
  • Follow mlir-rs/melior closely for breaking changes

Risk 2: Learning Curve

Impact: High (short-term) Probability: High

Issue: MLIR is complex; team needs to learn dialects, lowering passes, etc.

Mitigation:

  • Invest Month 4 in learning/prototyping
  • Use existing tutorials (Stephen Diehl, Jeremy Kun, Toy Tutorial)
  • Reference Mojo's approach (open-source in 2026)
  • Start simple: func + arith only, expand later

Risk 3: Debugging Complexity

Impact: Medium Probability: Medium

Issue: Multi-dialect lowering makes errors hard to trace

Mitigation:

  • Use mlir-opt --mlir-print-ir-after-all to see each pass
  • Implement Joule-specific error messages wrapping MLIR errors
  • Build tooling: joulec --emit-mlir, joulec --emit-llvm

Risk 4: GPU Backend Fragmentation

Impact: Low Probability: Low

Issue: NVPTX works well, but Metal/ROCDL might have gaps

Mitigation:

  • Prioritize NVIDIA (largest ecosystem)
  • AMD as secondary target (HIP is mature)
  • Metal as tertiary (smaller market share, but good for demos)
  • Accept some vendor-specific extensions (#[target(cuda)])
