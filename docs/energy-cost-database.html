The Joule Programming Language

Energy Cost Database

Overview

The energy cost database is a critical component of the Joule compiler's energy optimization system. It provides calibrated measurements of energy consumption (in picojoules) for individual CPU instructions, enabling the optimizer to make informed decisions about which code transformations will reduce energy usage.

Components

1. Cost Model (compiler/joule-energy/)

The core library that defines instruction types and their energy costs.

Key Types:

  • InstructionType: Enum of measurable CPU operations (31 types)

    • Integer: add, sub, mul, div, rem
    • Bitwise: and, or, xor, shl, shr
    • Float: add, sub, mul, div, sqrt
    • SIMD: f32x8/i32x8 operations
    • Memory: L1/L2/L3/DRAM loads
    • Branches: taken, not taken, mispredicted

  • InstructionEnergy: Energy cost for one instruction

    #![allow(unused)]
fn main() {
pub struct InstructionEnergy {
    pub base_cost_pj: f64,         // Base energy in picojoules
    pub thermal_multiplier: f64,   // Cost increase when CPU is hot
    pub stddev_pj: f64,            // Standard deviation
    pub sample_count: usize,       // Number of calibration samples
}
}

  • EnergyCostModel: The cost database

    #![allow(unused)]
fn main() {
pub struct EnergyCostModel {
    costs: HashMap<InstructionType, InstructionEnergy>,
}
}

Example Usage:

#![allow(unused)]
fn main() {
use joule_energy::{EnergyCostModel, InstructionType};

let model = EnergyCostModel::default_calibrated();

// Query cost
let int_add = model.get(&InstructionType::IntAdd).unwrap();
println!("int_add costs {} pJ", int_add.base_cost_pj);

// Calculate actual cost with thermal scaling
let thermal_factor = 0.5; // 50% thermal stress
let actual_cost = int_add.actual_cost(thermal_factor);
}

2. Benchmarking Tool (tools/energy-bench/)

Measures instruction energy using RAPL (Running Average Power Limit) on Linux.

Features:

  • Microbenchmarks: Execute instruction billions of times and measure energy
  • Statistical Analysis: Multiple runs with mean/stddev calculation
  • Thermal Testing: Measure cost difference between cold and hot CPU
  • Memory Patterns: Test L1/L2/L3/DRAM with different access patterns
  • JSON Export: Save calibrated model for use by optimizer

Benchmark Method:

#![allow(unused)]
fn main() {
fn bench_int_add() -> BenchResult {
    const OPERATIONS: u64 = 1_000_000_000;

    let monitor = EnergyMonitor::start()?;

    let mut result = 0u64;
    for i in 0..OPERATIONS {
        result = result.wrapping_add(i);  // The operation we're measuring
    }
    black_box(result);  // Prevent optimization

    let metrics = monitor.stop()?;

    // Energy per operation
    let energy_per_op_pj = (metrics.energy_joules * 1e12) / OPERATIONS as f64;

    BenchResult { energy_per_op_pj, ... }
}
}

Usage:

# Run all benchmarks (requires sudo on Linux for RAPL access)
sudo cargo run --release -p energy-bench -- all --iterations 20 --output costs.json

# Benchmark specific instruction
sudo cargo run --release -p energy-bench -- single int_add --iterations 10

# Test thermal impact
sudo cargo run --release -p energy-bench -- thermal int_mul

# Verify existing model
cargo run --release -p energy-bench -- verify --model costs.json

Default Calibration

The cost model includes default calibrated values measured on an Intel Core i7-10700K (14nm, 8 cores, 3.8-5.1 GHz) with DDR4-3200 RAM.

Key Insights from Measurements

  1. Memory Dominates Energy

    • DRAM load: 200 pJ (4000x more than int_add)
    • L3 load: 50 pJ (1000x more than int_add)
    • L1 load: 5 pJ (100x more than int_add)
    • Optimization: Keep data in registers, avoid memory access

  2. Division is Expensive

    • Integer div: 1.50 pJ (30x more than int_add)
    • Float div: 2.50 pJ (50x more than int_add)
    • Optimization: Replace division with multiplication by reciprocal

  3. SIMD is Energy-Efficient

    • 8x scalar f32 add: 2.40 pJ (8 × 0.30 pJ)
    • 1x SIMD f32x8 add: 0.80 pJ (3x energy savings)
    • Optimization: Vectorize loops when possible

  4. Thermal Impact is Real

    • Most instructions: 5-10% cost increase when hot
    • Complex operations: 15-25% increase
    • Optimization: Burst computation then idle (race to sleep)

  5. Compute vs Memory Trade-off

    • 1 DRAM load = 4000 integer adds
    • Optimization: Recompute cheap values rather than loading from memory

Usage in Optimizer

The energy optimizer (future component) will use this database to:

  1. Estimate Code Energy: Sum instruction costs for basic blocks
  2. Compare Transformations: Choose lower-energy alternatives
  3. Guide Optimizations:
    • Prefer SIMD over scalar operations
    • Replace division with multiplication
    • Eliminate redundant memory loads
    • Keep hot data in registers
    • Optimize memory access patterns (row buffer locality)

Example Optimization Decision:

#![allow(unused)]
fn main() {
// Original code (energy = 200 pJ load + 0.05 pJ add)
let x = array[i];
let y = x + 1;

// vs. Recompute (energy = 2 × computation)
// If computation < 100 pJ, recomputing is cheaper than loading!
}

Calibrating for Your System

Default values are estimates. For accurate optimization, calibrate on your target hardware:

Preparation

Linux (Recommended):

# Enable MSR access
sudo modprobe msr
sudo chmod +r /dev/cpu/*/msr

# Set CPU governor to performance (reduce frequency scaling noise)
sudo cpupower frequency-set -g performance

# Disable turbo boost (optional, for more consistent results)
echo 1 | sudo tee /sys/devices/system/cpu/intel_pstate/no_turbo

macOS:

# Requires root access for IOKit
sudo cargo run --release -p energy-bench -- all

Running Benchmarks

# Close all applications for minimal interference
# Run on AC power (not battery)

# Full calibration with 50 iterations per instruction
sudo cargo run --release -p energy-bench -- all --iterations 50 --output my_system_costs.json

# Takes ~30-60 minutes depending on system

Interpreting Results

Good calibration should show:

  • Low standard deviation (< 10% of mean)
  • Consistent ordering (int_add < int_mul < int_div)
  • Memory hierarchy preserved (L1 < L2 < L3 < DRAM)

High variance indicates:

  • Background processes interfering
  • Thermal throttling during measurement
  • CPU frequency scaling
  • Measurement granularity limits (for very cheap operations)

Using Custom Calibration

#![allow(unused)]
fn main() {
// Load from JSON file
let json = std::fs::read_to_string("my_system_costs.json")?;
let model = EnergyCostModel::from_json(&json)?;

// Use in optimizer
let optimizer = EnergyOptimizer::new(model);
}

Limitations

Measurement Granularity

  • RAPL resolution: ~15 µJ, sampling: ~1ms
  • Very cheap operations (< 1 pJ) have high relative error
  • Need billions of iterations for accurate measurement

Instruction Mix Overhead

  • Benchmarks include loop overhead (branch, increment)
  • CPU front-end effects (decode, fetch)
  • Relative costs more reliable than absolute values

System Variation

Energy varies with:

  • Temperature (thermal throttling)
  • Voltage (DVFS)
  • Process variation (chip-to-chip)
  • Background tasks
  • Memory configuration

Model Simplifications

  • Assumes instructions are independent
  • Ignores instruction-level parallelism
  • Doesn't model cache behavior in detail
  • Branch prediction is simplified

Use these values as estimates for optimization decisions, not exact measurements.

Integration with MIR Optimizer

The cost database is designed to integrate with the MIR (Mid-level IR) optimizer:

#![allow(unused)]
fn main() {
// Future MIR optimizer pseudocode
impl MirOptimizer {
    fn optimize_with_energy(&mut self, mir: &mut Mir, model: &EnergyCostModel) {
        // Calculate energy cost of current code
        let original_cost = self.estimate_energy(mir, model);

        // Try transformation
        let transformed = self.apply_optimization(mir);
        let new_cost = self.estimate_energy(&transformed, model);

        // Keep transformation if it reduces energy
        if new_cost < original_cost {
            *mir = transformed;
        }
    }

    fn estimate_energy(&self, mir: &Mir, model: &EnergyCostModel) -> f64 {
        mir.instructions.iter()
            .map(|inst| self.instruction_to_cost(inst, model))
            .sum()
    }
}
}

This is parallel work - the cost database is ready to use whenever the MIR optimizer is implemented!
